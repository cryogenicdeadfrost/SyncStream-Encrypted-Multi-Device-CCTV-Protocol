# SyncStream Encrypted Multi-Device CCTV Protocol

SyncStream is a small, transport-agnostic C++20 SDK for building encrypted phone-to-camera and multi-device CCTV control channels. It is designed to be consumed like a normal system library: one stable umbrella header, one CMake target, and optional pkg-config metadata.

The important distinction is deliberate: SyncStream secures the **control plane**. It does not pretend to be an NVR, RTSP server, WebRTC stack, or cloud service. Your application owns the transport and camera/media layer. SyncStream gives that application a stable API for authenticated commands, replay protection, timestamp checks, key derivation, wire encoding, and request/response handling.

## What the library provides

- AES-256-GCM authenticated encryption with AAD
- Random 96-bit GCM nonces generated by OpenSSL
- Secure cleanup of key and plaintext buffers
- Compact binary control envelopes
- Timestamp skew enforcement
- Replay detection
- Key derivation and versioned key staging through Keychain
- Command policy and per-device rate limiting through EdgeHub
- A complete high-level phone/camera API through CameraClient and CameraServer
- Versioned wire encoding and strict malformed-input checks
- Request IDs and authenticated request/response correlation
- Camera-oriented commands: arm, disarm, sync, ping, status, stream configuration, recording, and PTZ
- No mandatory networking, cloud account, database, or paid service
- Stable umbrella header: #include <syncstream/syncstream.hpp>
- Installable CMake package: find_package(SyncStream CONFIG REQUIRED) and SyncStream::syncstream
- pkg-config metadata for non-CMake consumers
- Zero-setup standalone phone/camera loopback example with no real camera or network
- Optional OpenCV capture example showing SyncStream controlling a real local camera while OpenCV handles video

## The high-level API

Applications should normally use syncstream/api.hpp rather than constructing RelayCore directly.

Phone/client side:

~~~cpp
#include "syncstream/api.hpp"

auto key = syncstream::mint_key();

syncstream::CameraClient phone(key);

const std::vector<std::uint8_t> settings{
    '1', '0', '8', '0', 'p', ':', '3', '0'
};

auto wire = phone.make_command(
    "camera-01",
    syncstream::Cmd::set_stream,
    settings
);

// Send wire using your transport:
// WebSocket, TCP, BLE, QUIC, gRPC, USB, etc.
~~~

Camera/relay side:

~~~cpp
#include "syncstream/api.hpp"

syncstream::CameraServer camera(key);

auto request = camera.open_wire(wire);

if (request.command == syncstream::Cmd::set_stream) {
    // Validate device capabilities and apply the setting.
}

auto response = camera.make_response(
    request,
    true,
    std::vector<std::uint8_t>{'o', 'k'}
);

// Send response back over the transport.
~~~

The transport is intentionally not hidden inside SyncStream. This keeps the library usable on Android, iOS, Linux gateways, embedded systems, desktop applications, and custom transports without forcing one networking stack on every consumer. The optional capture example follows the same rule: SyncStream controls camera state while a media library owns frame capture and recording.

## Recommended architecture

~~~
Phone application
      |
      | transport of your choice
      v
SyncStream CameraClient
      |
      | authenticated binary envelope
      v
SyncStream CameraServer
      |
      v
Camera control / ONVIF / RTSP application
~~~

For a larger deployment:

~~~
Phone -> SyncStream -> Edge Gateway -> SyncStream -> Camera
                         |
                         +-> ONVIF / RTSP / recording
~~~

SyncStream should sit beside the media stack, not inside the video data path. CCTV video is a continuous high-bandwidth stream. SyncStream is for commands, state changes, acknowledgements, and other control messages.

## Wire format

The public WireCodec turns the authenticated envelope into bytes suitable for any byte-oriented transport.

The current envelope contains:

~~~text
version
sequence
timestamp
96-bit nonce
ciphertext length
ciphertext
128-bit authentication tag
~~~

Versioned envelopes additionally carry the active key version.

Malformed, truncated, oversized, or unsupported-version messages are rejected before application processing.

## Key model

The simplest deployment is a pre-shared 256-bit key:

~~~cpp
auto key = syncstream::mint_key();
syncstream::CameraClient phone(key);
syncstream::CameraServer camera(key);
~~~

For a deployment where a key must be derived from a master secret, use Keychain and its HKDF-SHA256 staging/activation API.

Do not hard-code production keys into mobile source code. A real deployment should provision a device-specific key during enrollment and store it using the platform's secure storage facilities.

## What SyncStream does not do

SyncStream deliberately does not provide:

- Camera discovery
- RTSP ingestion
- Video recording
- WebRTC
- User authentication
- Camera passwords
- Cloud hosting
- NAT traversal
- Push notifications
- Persistent device databases
- Persistent/shared replay storage by default
- Device enrollment, approval, provisioning, rotation, or revocation
- User authentication or user-to-camera authorization
- Secure mobile key storage itself
- Camera discovery
- NAT traversal, TURN, signaling, or connection brokering
- Video codecs, frame transport, media recording, or NVR storage
- Vendor-specific ONVIF/RTSP/WebRTC implementations
- Mobile UI, notifications, background-service lifecycle, or permissions
- Cloud synchronization or remote account management
- JNI/Kotlin, Swift, Python, or Rust bindings yet

Those belong to the application built around the library.

That is a feature, not a missing dependency. The library can therefore be embedded into a phone application, a Linux edge agent, a desktop CCTV client, or a larger server without dragging an entire surveillance platform into the dependency graph.

## Use it like a normal C++ library

From an installed SDK:

~~~cpp
#include <syncstream/syncstream.hpp>

auto key = syncstream::mint_key();
syncstream::CameraClient phone(key);
auto wire = phone.make_command("camera-01", syncstream::Cmd::get_status);
~~~

CMake:

~~~cmake
find_package(SyncStream CONFIG REQUIRED)
target_link_libraries(my_app PRIVATE SyncStream::syncstream)
~~~

For a source-tree integration:

~~~cmake
add_subdirectory(SyncStream-Encrypted-Multi-Device-CCTV-Protocol)
target_link_libraries(my_app PRIVATE SyncStream::syncstream)
~~~

The installation also provides syncstream.pc for pkg-config based builds.

For a first smoke test, build syncstream_standalone_phone_test. It simulates both endpoints in one process, so a developer can verify the public API, authenticated wire encoding, request/response correlation, and protocol processing before writing any networking or camera code.

## Security model

SyncStream uses authenticated encryption rather than encryption alone. AES-GCM authenticates both ciphertext and additional authenticated data.

The library rejects:

- Modified ciphertext
- Modified AAD
- Invalid authentication tags
- Replayed authenticated envelopes
- Messages outside the configured clock-skew window
- Truncated wire frames
- Oversized wire fields
- Unsupported wire versions

Replay-cache state is intentionally kept in the library instance. Applications operating across multiple processes or persistent restarts should provide a durable/shared replay strategy at the application layer before treating a deployment as horizontally scalable.

The protocol uses a fresh random 96-bit AES-GCM nonce for each encryption operation. Nonce/key uniqueness is a fundamental AES-GCM requirement, so applications must not replace this behaviour with a reused fixed nonce. NIST explicitly identifies IV uniqueness as critical to GCM security.

## Design goal

The goal is not to make every application depend on a giant CCTV framework.

The goal is to make this work:

~~~cpp
auto wire = phone.make_command(
    "front-door",
    syncstream::Cmd::start_recording
);

// transport(wire);

auto request = camera.open_wire(wire);

// execute_camera_command(request);

auto reply = camera.make_response(request, true);

// transport(reply);
~~~

That is the contract.

A developer should be able to take SyncStream, choose their own transport and camera/media implementation, and have secure CCTV control without reverse-engineering the protocol.

## Roadmap

The protocol core is now intended to be a reusable API library.

Future work belongs around the core:

1. Stable ABI / C bindings
2. Android JNI and Kotlin wrapper
3. Swift/iOS wrapper
4. Rust and Python bindings
5. Optional WebSocket transport adapter
6. Device enrollment and per-device key provisioning
7. Persistent replay-store interface
8. Fuzzing and protocol conformance suite
9. SyncStream Station as the user-facing UI/application layer

SyncStream Station can therefore consume this repository as its protocol dependency instead of duplicating or modifying the security implementation.
